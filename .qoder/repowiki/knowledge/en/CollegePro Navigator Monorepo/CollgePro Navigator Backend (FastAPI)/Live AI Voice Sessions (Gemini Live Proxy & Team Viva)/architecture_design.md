Two-layer split inside this leaf:

- API layer (`backend/api/live.py`, `backend/api/viva.py`): FastAPI routers expose a REST lifecycle for pre-generated mock vivas (`/api/viva/...`) and a single WebSocket endpoint `/ws/live/{mode}/{session_id}` for the live conversational flow. The WS handler authenticates via token, loads session/project context from Supabase, resolves a scenario from `ai.registry`, builds a `LiveConnectConfig`, then runs two concurrent async tasks — `client_to_gemini` (mic PCM16 / JPEG frames / text) and `gemini_to_client` (PCM24 audio + transcripts + tool calls). A per-session owner lock (`_active_live_owners`) prevents duplicate greetings on remounts, and a `_MIC_GATE_SAFETY_SECONDS` timer guarantees the mic is never gated forever if the model fails to emit `turn_complete`. Finalization runs in a worker thread via `asyncio.to_thread(LivePersistence.finalize)` so the socket can close while the report LLM call completes.

- Engine layer (`backend/ai/live_service.py`, `team_live_service.py`, `team_room.py`): `live_service` owns the Gemini SDK client singleton, model fallback chain (`connect_with_fallback` tries configured model then `gemini-3.1-flash-live-preview` → `gemini-2.5-flash-live-preview`), system-instruction builder (`build_system_instruction` with mode-specific playbooks, persona blocks, language directives, transcription hints, VAD tuning), tool declarations (`log_observation`, `flag_moment`, `record_question`, `score_response`, `end_session`), and audio framing helpers (`response_audio_chunks`, `send_audio`). `team_live_service` reuses those helpers but swaps the playbook/tools for a group-viva variant (`call_on_participant` instead of solo addressing). `team_room.py` implements a `VoiceRoom` that fans one shared Gemini connection out to multiple WebSockets, enforces floor control (only the participant named by `call_on_participant` has their mic forwarded), and persists per-participant Q&A into `viva_questions` + `team_viva_scores`.

Dependency direction: `api/*` depends on `ai.live_service` and `ai.team_*`; `ai.team_live_service` imports only shared helpers from `ai.live_service`; neither side imports the other back. All DB access goes through `core.database.get_supabase()`; auth via `core.deps.user_from_token` / `get_current_user`.

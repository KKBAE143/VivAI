Two independent FastAPI routers under `backend/api/` expose the functionality: `analytics.py` registers `/api/analytics` with four GET endpoints (`/dashboard`, `/activity`, `/trends`, `/leaderboard`) that query Supabase tables directly via `core.database.get_supabase()`, while `readiness.py` registers `/api/readiness` with a GET for the readiness score, a PUT `/model` to switch between v1/v2 DRS models, a GET `/benchmarks` delegating to `benchmark_service`, and a POST `/pitch` for stateless pitch evaluation. Business logic is split one-way: the API layer delegates composite-score computation to `services/readiness_service.py::compute_readiness`, which selects between model v1 (activity-focused: viva/presentation/coverage/consistency/project) and model v2 (skill-focused: technical_depth/communication/coverage/confidence/structure) based on the user's `profiles.drs_model` field. Both routers depend on `core.deps.get_current_user` for authentication; the pitch endpoint additionally calls `ai.gemini_service.generate_json` for LLM-based evaluation and triggers side effects through `services.activity_service.log_activity` and `gamification_service.award_xp`. There are no cross-imports between the two routers — dependency direction is strictly API → service → Supabase client.

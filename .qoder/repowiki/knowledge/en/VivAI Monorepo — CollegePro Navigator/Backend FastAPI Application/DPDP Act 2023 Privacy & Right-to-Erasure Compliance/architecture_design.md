Three-layer leaf module implementing the DPDP compliance phase:
- `backend/api/privacy.py` — FastAPI `APIRouter` mounted at `/api/privacy` with four authenticated endpoints (`/consent`, `/consent-status`, `/delete-my-data`, `/delete-status`) plus two public policy/grievance endpoints. Consent state is read from the user's profile row; deletion requests are persisted in a `data_deletion_requests` table before delegating to the service.
- `backend/services/deletion_service.py` — pure function `execute_deletion(profile_id)` that cascades deletes across Supabase tables in dependency order (viva_questions via session_ids first, then files/code_snapshots storage + rows, then all `_PROFILE_TABLES`, finally anonymizing the `profiles` row) and records which tables were touched in `deleted_tables JSONB`. Errors leave the request in `processing` for manual intervention rather than rolling back.
- `backend/migrations/005_dpdp_compliance.sql` — additive, idempotent schema migration adding five `profiles` columns (`consent_accepted_at`, `consent_version`, `is_minor`, `parental_consent_at`, `data_deletion_requested_at`) and three new tables: `consent_log` (immutable audit of ToS/privacy/parental consent), `data_deletion_requests` (pending→processing→completed lifecycle), and `audit_log` (sensitive-access trail). All statements use `IF NOT EXISTS` / `ADD COLUMN IF NOT EXISTS` guards.

Dependency direction: API → service → Supabase client (`core.database.get_supabase`); no cross-import between the other backend modules. Policy text and version are embedded constants in the router so the endpoint stays stateless.

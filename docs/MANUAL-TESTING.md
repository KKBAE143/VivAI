# Manual testing guide

Every user-facing feature in VivAI, in the order you should walk it.

## How to read this

Each check has three parts: **how** (what you click or run), **expect** (what a working build does), and where relevant a **note** explaining a trap. Anything marked **VERIFY** is something derived from reading the code but never observed running — treat a mismatch there as a documentation bug first, not necessarily a product bug.

Two honesty markers you will see a lot:

- **BLOCKED** — cannot pass until a prerequisite in §1 is done (an unset env var, or an institution not yet marked verified). Do not log these as failures.
- **KNOWN BUG** — already understood to be broken. Confirm the symptom matches, then move on. Do not spend time debugging it.

Nothing in this document has been executed in a browser. It was written from the source, so its value is telling you _where to look_ and _what "correct" means_, not certifying that any of it currently passes.

### 1.3 Test accounts

You need five accounts. Creating them is itself the first test pass (§2).

| Account                | Role    | How to get it                                                                   |
| ---------------------- | ------- | ------------------------------------------------------------------------------- |
| `student1`             | student | Normal signup                                                                   |
| `student2`, `student3` | student | Normal signup — **needed for Team Viva, which requires 3 participants minimum** |
| `admin1`               | admin   | Signup, then pick "admin" in onboarding and create an institution               |
| `faculty1`             | faculty | See the warning below                                                           |

> **Faculty cannot be created through the UI.** Claiming "faculty" during onboarding parks the claim as `institution_members.requested_role` and leaves `profiles.role = 'student'` on purpose — otherwise any student could self-promote and read classmates' reports. The approval endpoints exist (`GET /api/institution/pending-faculty`, `POST /api/institution/approve-faculty`, both `require_admin`) but **no screen calls them**. So to get a faculty user, either call `POST /api/institution/approve-faculty` from Swagger as `admin1`, or set `profiles.role = 'faculty'` and `profiles.institution_id` by hand in Supabase.

For §15 you also need `institutions.verified_at` set by hand — self-serve institutions are deliberately unverified, and the cohort-data endpoints refuse until someone marks them verified "at sale time".

## 2. Read this before you start clicking

### 2.1 Fixed in this pass, never seen in a browser

**Team Viva could not connect at all.** Two separate faults, both invisible to the test suite because the unit tests drive the room object directly with a fake socket:

1. The browser opened `/ws/team-viva/{id}` while the server serves `/api/advanced/ws/team-viva/{id}` (that router carries an `/api/advanced` prefix; `live.router` does not, hence the asymmetry with `/ws/live/...`).
2. The handler accepted the WebSocket and then `VoiceRoom.connect` accepted it again, which raises `RuntimeError`.

§13 is therefore the highest-value section in this document and the least certain.

**Team Viva records were readable by anyone.** `GET /team-viva/sessions/{id}` and `/{id}/report` required only a valid token — any authenticated user could read any team's assessment by id, and the report handler never even loaded the session. Both now go through the same access check the WebSocket uses. Verify at §13.20.

**Privacy consent was never enforced.** `require_consent` existed and was wired to nothing. It now gates every endpoint that starts recording or processing a student. Because the signup form was the only thing that ever recorded consent, **every Google sign-in account has none**, so a consent prompt now appears in the app shell for those accounts. Verify at §3.21.

**Structured refusals were unreadable.** The consent and role gates raise `{error, message}`, which the frontend error parser dropped — every one of them showed "Request failed (403)". They now show the real message.

### 2.3 Dead ends — features with no UI path

Do not hunt for these screens; they do not exist.

- **Faculty approval queue.** Onboarding tells a faculty claimant they need admin approval, and no screen anywhere lets an admin approve. §1.3 works around it.
- **Per-student coverage tracking.** Nothing guarantees the AI called on every Team Viva participant. A student who was never asked a question cannot be graded — relevant to §13.9.
- **In-app "how this works / what this does not do" explainers.** Not built.
- **The sentiment API** (`/api/advanced/sentiment/*` and `WS /api/advanced/ws/sentiment/{id}`) is fully orphaned. Despite its filename, `/advanced/sentiment-analysis` runs on the presentation + live-coach path instead. Test the sentiment API from Swagger (§16) or not at all.
- **The whole REST viva turn lifecycle** (`/start`, `/answer`, `/skip`, `/hint`, `/end`, `/transcript`) has no caller — the live WebSocket drives sessions instead. Same for the REST presentation turn endpoints. §16 covers them.

### 2.4 Behaviour that changed with the security fixes

Both fixes make previously-permitted things fail. Expect these, and do not log them as regressions:

- Reading a Team Viva session or report you are not a participant in, or faculty of, now returns **403**. An unknown session id now returns **404** where the report used to return an empty object.
- Creating any session — viva, presentation, team viva, code-aware, sentiment — or submitting a pitch now returns **403 `consent_required`** if the account has no consent on record. Reading your own reports, and the deletion endpoint, are deliberately _not_ gated: withdrawing consent must not make the right to erasure unreachable.

### 2.5 Live evaluation moved off function calling

`LIVE_TOOLS_ENABLED = False` in `backend/ai/live_service.py`. The examiner no longer has `record_question`, `score_response`, `log_observation` or `end_session`. This was the root cause of the silent-examiner and duplicate-caption cycle: a native-audio turn that emits a function call can carry no audio at all, and stalls waiting for a tool response.

**The live evaluation panel still works.** It is now fed by `backend/ai/turn_grader.py`, which grades each exchange from the transcript on a separate ordinary text call once the answer finishes. The client protocol is unchanged — the same `question` and `score` events, correlated by id. What changed:

- **Entries arrive a second or two after each answer, not during it.** That is the grading call completing. An entry that never appears for one answer is acceptable (see the skip conditions below); a session where nothing ever appears is a fault.
- **Very short answers are skipped on purpose.** Under 6 words — "yes", "I don't know", "sorry, repeat that" — is not graded live. It still reaches the final report.
- **Language never decides whether an exchange is graded.** The only deterministic filters are lengths — under 6 words of answer, under 3 words of examiner turn — which behave identically in every language. Whether it was really a question and really an answer is decided by the model, via a `gradable` field, because it reads all thirteen supported languages and no hand-written word list can. The question shown in the panel is the one the model identifies, quoted in the language it was asked. Worth spot-checking on a Telugu or Marathi session (§12.1.4).
- **Grading is capped at 2 in flight per session.** Answer faster than the key can grade and one entry is dropped rather than queued. The report is unaffected.
- **A grading failure is silent by design.** Timeout, 429, or bad JSON just means a quieter panel. It must never interrupt the conversation.
- **Sessions still end themselves, from the transcript instead of a tool call.** Three conditions, all required: the planned number of questions has been asked, then 25 seconds of silence from both sides, then a separate model call confirms the last turn was a closing remark rather than a question. That confirmation has to be a model call — "that's everything from my side" is different in every supported language — and it **fails closed**, so an unreachable or uncertain verdict leaves the session open. Any activity from either side disarms the whole thing. The other endings are unchanged: the student pressing End, the server clock at the chosen duration plus a 45s grace, and the 30-minute fallback ceiling for a session with no duration configured.
- **`log_observation` has a deterministic replacement.** `backend/ai/delivery_observer.py` produces pace, conciseness and filler observations from the words and timing already recorded, with no model call. **Filler claims are gated by language**: English sessions get both the criticism and the praise; Hinglish/Tenglish/Tanglish get the criticism only, because English fillers found in blended speech are real but their absence cannot be verified; a regional-language session gets neither, because "almost no filler words" derived from an English word list is a compliment handed out for the language the student chose.
- **`flag_moment` has a replacement too.** `backend/ai/vision_observer.py` glances at the newest video frame every 30 seconds on a separate vision call — never on the voice socket — and pushes what it sees to the panel. Runs only when the session actually has video: camera notes (eye contact, posture, framing, expression, energy) for a coach session, screen notes (readability, density, visual aids) for a presentation. A viva has no video and costs nothing. Bounded at 60 calls per session as a cost guard; the interval and cap are constants at the top of `backend/api/live.py`. Three things it is built not to do: claim anything it cannot see in the frame (an unrecognised dimension or missing evidence is dropped), describe one moment as a pattern, or comment on appearance, clothing, the room or the background — none of which is delivery, and all of which a vision model volunteers unprompted. Frame notes are capped at `medium` confidence because one frame is an inference, not a measurement.
- **Team Viva still uses tools.** `backend/ai/team_live_service.py` is untouched — the room needs `call_on_participant` to know whose microphone to open. Do not read solo behaviour across to §13.

Reverting to tools is one flag; the declarations and handlers are still in place.

## 18. Recording results

For each failure, capture: the check number, what you saw, the `X-Request-Id` from the failed response if there was one, and the matching `diagnostics/` event. That triple is enough to fix without reproducing.

Triage order when several things fail at once:

1. §1 prerequisites — a missing key or an unapplied migration explains whole sections at once.
2. §13.1 — if the Team Viva socket does not connect, everything under §13 fails for one reason.
3. Anything in §2.2 — already known, do not re-investigate.

## 19. What this document cannot cover

- **Assessment quality.** Whether a score is _right_ is not a pass/fail check. Run a viva you could grade yourself and judge the marks against your own.
- **Acoustics at scale.** Three participants in one room, on real hardware, over real networks. Nothing here substitutes for that.
- **Concurrency.** Two faculty taking over at once, a lead ending a viva mid-answer, simultaneous drags on one board.
- **Load.** Several live sessions on one backend; every live session holds a Gemini connection.
- **Cloudflare.** All of this is local. The Nitro `cloudflare-module` target has its own failure modes, particularly around WebSockets.
- **Accessibility and WCAG.** Aria wiring exists on the newer screens, but real validation needs a screen reader and expert review.
- **The accreditation claim.** The pitch assumes NBA/NAAC require documented outcome assessment, which makes these reports an accreditation artifact. Nobody has checked that against actual NBA criteria. It is not a software test, but it is the load-bearing assumption under the product.

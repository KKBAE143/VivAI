Two FastAPI routers live under `backend/api/`: `analytics.py` registers `/api/analytics` with four GET endpoints (`/dashboard`, `/activity`, `/trends`, `/leaderboard`) that query Supabase tables directly via `core.database.get_supabase()`, while `readiness.py` registers `/api/readiness` with a GET for the readiness score and a POST `/pitch` for stateless pitch evaluation. The business logic is split: `readiness.py` delegates the composite-score computation to `services/readiness_service.py::compute_readiness`, which aggregates data from `viva_sessions`, `presentation_sessions`, `viva_questions`, and `projects` tables using weighted components (WEIGHTS dict summing to 1.0) and returns a band/label plus suggested actions. Both routers depend on `core.deps.get_current_user` for authentication, and the pitch endpoint additionally calls `ai.gemini_service` for LLM-based evaluation and `services.activity_service.log_activity` / `gamification_service.award_xp` for side effects. Dependency direction is one-way: API layer → service layer → Supabase client; no cross-imports between the two routers.
